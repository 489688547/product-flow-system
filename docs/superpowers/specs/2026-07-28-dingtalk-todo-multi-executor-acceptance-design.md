# 多人钉钉待办完成进度与产品负责人验收设计

## 背景

产品任务可以把一条钉钉个人待办同步给多名执行人，但当前系统只读取当前登录人的整体完成状态，并直接把远端完成映射为产品任务完成。发起人和产品负责人无法看到每位执行人的状态，也没有最终验收步骤。

任务类别仍包含“会前准备”“决策”等历史分类，用户难以判断应该同步待办还是预约会议。必需任务虽然在前端缺少交付物时会禁用完成，但缺少服务端验收规则。

## 已确认规则

1. 任务类别只保留“待办任务”和“会议”。
2. 钉钉待办执行人逐人完成，系统显示完成分数。
3. 产品负责人占最后一个验收名额；五名普通执行人初始显示 `0/6`。
4. 产品负责人同时出现在执行人选择中时不重复计数，也不作为普通执行人发送。
5. 普通执行人全部完成后，产品负责人才能最终验收。
6. 必需任务没有任何已绑定交付物时，产品负责人不能完成验收。
7. 任何普通执行人在钉钉取消完成后，未验收任务的分数回退；已经验收的任务重新打开，产品负责人需要再次验收。

## 非目标

- 不为每名执行人创建一条重复待办。
- 不新增评论、催办、提醒或钉钉消息通知。
- 不改变会议的钉钉日程同步方式。
- 不新增数据库表或环境配置。
- 不让浏览器直接调用钉钉开放平台。

## 方案比较

### 方案 A：一条待办，按执行人读取状态

保留一个 `taskId`，服务端使用同一 `taskId` 分别读取各执行人的任务详情，聚合为逐人状态。

优点：钉钉内只有一条协作待办；延续现有绑定；迁移成本低。缺点：读取次数等于执行人数，需要严格限制并发。

### 方案 B：每位执行人一条待办

每人创建独立 `taskId`，系统聚合多条待办。

优点：状态天然独立。缺点：创建、更新和清理更复杂；发起人的待办列表容易重复；现有一对一绑定需要迁移。

### 方案 C：只显示整体完成

继续读取一个整体状态，只增加产品负责人验收。

优点：改动最小。缺点：无法回答“谁完成了”，不满足已确认需求。

采用方案 A。

## 任务类别

公开类别固定为：

- `待办任务`：显示钉钉待办同步入口。
- `会议`：显示钉钉日程预约入口。

历史类别按兼容规则归一：

- `会前准备`、`决策`、`会后交付`、`准入条件` → `待办任务`
- `会议/决策` → `会议`

新增任务默认使用 `待办任务`。数据库中的旧值在现有共享状态规范化时兼容读取，不执行一次性数据库迁移。

## 完成模型

### 有钉钉执行人的待办任务

有效普通执行人是同步选择中排除产品负责人后的 unionId 去重集合。

```text
总人数 = 有效普通执行人数 + 1 个产品负责人验收位
已完成人数 = 钉钉已完成普通执行人数 + 产品负责人已验收值
```

示例：

- 五名普通执行人均未完成：`0/6`
- 两名普通执行人完成：`2/6`
- 五名普通执行人完成：`5/6 · 待产品负责人验收`
- 产品负责人验收：`6/6 · 已完成`

如果选择中只剩产品负责人，同步按钮保持禁用并提示“请至少选择一位其他执行人”；不创建没有普通执行人的钉钉待办。

### 未同步待办和会议

没有普通执行人状态时只保留产品负责人验收位，显示 `0/1` 或 `1/1`。会议预约成功不等于任务完成，仍由产品负责人验收。

### 重新打开

- 验收前：执行人取消钉钉完成，只减少分子。
- 验收后：任一执行人取消完成，系统自动把最终验收置为未完成并回到 `N/总数`。
- 产品负责人可以主动取消自己的最终验收，任务回到“待验收”，不修改任何执行人的钉钉状态。

## 数据模型

复用共享状态中的任务对象，新增可选字段：

```js
task.dingTodo.executorStatuses = [
  {
    unionId: "union-id",
    isDone: true,
    observedAt: "2026-07-28T10:00:00.000Z"
  }
];

task.acceptance = {
  accepted: true,
  acceptedByUnionId: "product-manager-union-id",
  acceptedAt: "2026-07-28T10:05:00.000Z"
};
```

规则：

- `task.done` 继续作为任务最终完成的兼容字段，仅在产品负责人验收成功时为 `true`。
- `dingTodo.remoteDone` 表示所有有效普通执行人是否完成，不再直接等同于 `task.done`。
- 不保存供应商原始响应、手机号、令牌或不必要的人员资料。
- 人员姓名从现有组织缓存和 `dingTodo.executorNames` 读取；状态记录只保存稳定 unionId。

旧任务兼容：

- 旧任务 `task.done=true` 保持已完成，并补为兼容验收状态。
- 已绑定待办但没有逐人状态时显示“正在读取完成进度”，首次成功读取后建立状态数组。
- 旧的单执行人远端完成不再自动视为最终验收。

## 服务端数据流

### 逐人状态读取

扩展现有钉钉待办列表路由：

1. 服务端从当前业务数据库读取产品任务和可信待办绑定。
2. 根据任务中保存的执行人 unionId 生成 `taskId × executorUnionId` 查询对，不接受浏览器自报执行人身份。
3. 使用应用访问凭证读取 `/users/{executorUnionId}/tasks/{taskId}`。
4. 单次最多处理 40 个查询对，并发上限保持 4。
5. 返回任务级 `executorStatuses`，并通过现有原子共享状态路径保存最新状态。
6. 无法读取的执行人保留上次成功状态，并返回部分覆盖警告；不能把未读取当作未完成。

产品负责人、原创建人和任务执行人可以触发刷新；页面展示仍按现有产品进度可见权限执行。

### 产品负责人验收

新增内部任务完成接口，由服务端执行：

1. 校验当前会话 unionId 等于产品的 `productManagerUnionId`。
2. 待办任务已同步时，校验所有有效普通执行人已完成且状态覆盖完整。
3. 必需任务校验至少存在一个 `taskId` 匹配的交付物。
4. 原子写入 `task.acceptance` 和 `task.done`。
5. 取消验收只清除产品负责人验收，不改钉钉执行人状态。

稳定错误：

- `TASK_PRODUCT_MANAGER_REQUIRED`
- `TASK_EXECUTORS_INCOMPLETE`
- `TASK_EXECUTOR_STATUS_INCOMPLETE`
- `TASK_DELIVERABLE_REQUIRED`
- `TASK_COMPLETION_VERSION_CONFLICT`

浏览器不通过普通整表更新绕过验收规则。共享状态写入需要拒绝未经授权的 `task.done` 变化。

## 页面设计

任务操作区使用一个紧凑进度触发器：

```text
钉钉 · 2/6 已完成
```

状态：

- `0/6 已完成`
- `2/6 已完成`
- `5/6 待验收`
- `6/6 已完成`
- `完成进度读取不完整`

点击后展开轻量人员面板，按以下顺序展示：

1. 普通执行人：头像/姓名、已完成或未完成。
2. 产品负责人：姓名、待验收或已验收。
3. 状态更新时间和读取警告。

产品负责人看到“确认完成”按钮；其他人只读。按钮禁用时就近显示唯一原因：

- “还有 2 位执行人未完成”
- “完成状态尚未读取完整”
- “必需任务需要先添加交付物”

键盘可打开人员面板、逐项读取状态并关闭；进度不能只用颜色表达。窄屏面板占满可用宽度，不产生横向滚动。

## 异常处理

- 单人查询失败：保留该人的上次状态，标记覆盖不完整，禁止最终验收。
- 钉钉限流：遵循现有退避，不重复并发刷新。
- 产品负责人未配置：显示“请先设置产品负责人”，禁止最终验收。
- 组织成员已停用：保留已绑定身份及最后状态，提示重新同步执行人。
- 并发验收或共享状态变化：返回版本冲突并刷新，不覆盖他人的新状态。

## 测试与验收

自动化测试至少覆盖：

1. 类别只暴露两项，历史类别正确归一。
2. 产品负责人从普通执行人中去重，五名普通执行人得到六个完成位。
3. 逐人读取成功、部分失败、限流和 40 对上限。
4. 非产品负责人、执行人未完成、状态不完整、必需交付物缺失时服务端拒绝验收。
5. 执行人取消完成后分数回退，已验收任务重新打开。

浏览器验收覆盖桌面、窄屏、键盘和钉钉 WebView。真实钉钉验收只使用明确授权的测试账号；创建、完成、取消完成和清理测试待办分别记录，不向其他员工发送测试任务。

## 迁移与回滚

- 不新增 D1 表、绑定、变量或秘密。
- 新字段全部可选，现有共享状态规范化负责兼容。
- 回滚代码时旧版本忽略新增字段；已创建钉钉待办继续存在。
- 若逐人读取异常，可回滚到只读同步状态，但不得恢复“任一执行人完成即自动完成产品任务”的旧规则。
