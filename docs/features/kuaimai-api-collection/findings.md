# 快麦订单接口采集：生产环境验证结论

日期：2026-07-29。全部结论在生产页面上实测得出。

## 最重要的事实：源头数据一直都在

用 `/trade/search/count` 按业务日查询订单总数：

| 业务日 | 快麦订单数 | 系统当时的显示 |
|---|---|---|
| 2026-07-23 | 6408 | 正常 |
| 2026-07-24 | 5874 | 正常 |
| 2026-07-25 | **6556** | **整日断档** |
| 2026-07-26 | **6625** | **残缺，约 7%** |
| 2026-07-27 | **6732** | **残缺，约 8%** |
| 2026-07-28 | 6606 | — |

**快麦里这几天订单量完全正常。** 缺口不是「采不到数据」，而是采集链路
（网页导出 → 下载 → 归档 → 入库）在中途丢失，源头始终完好。

这改变了问题定性：不是数据缺失，是采集管道故障。

## 接口

```
POST /trade/search          订单列表
POST /trade/search/count    总数（用于分页）
```

- 请求体为 `application/x-www-form-urlencoded`，**不是 JSON**
- 关键参数：`timeType`、`startTime`、`endTime`（毫秒时间戳）、`pageNo`、`pageSize`
- 其余为筛选项，从页面实际请求继承即可
- **无签名参数，无风控拦截**，鉴权仅依赖 Cookie

## 响应

```
{ api_name, clueId, qTime, result: 1, data: { page: {...}, total: <number> } }
```

总数在 `data.total`，**不在 `data.page`** 内。`page` 只含
`offsetRow`/`pageNo`/`pageSize`/`startRow`，没有 `totalRow` 或 `totalPage`。

## 与抖音路线的差异

抖音罗盘的日期组件只响应 `isTrusted` 事件，且部分接口带一次性签名；
快麦这两个接口是普通表单 POST，**没有这些障碍**，实现难度显著更低。

## timeType 必须为 created，且必须白名单校验

`PRODUCT.md` 规定统一口径使用**订单创建时间**。实测 2026-07-25：

| `timeType` | 订单数 |
|---|---|
| `created` | **6955**（订单创建时间，正确口径） |
| `pay_time` | 6556（付款时间，页面默认） |
| `create_time` / `order_time` / `trade_time`（编造值） | 6556 |

两者相差 399 单，约 6%。**页面默认的 `pay_time` 不符合系统口径。**

更危险的是：接口对无效 `timeType` **静默回落到默认值**，既不报错也不提示。
编造的三个值全部返回 6556。因此实现必须对 `timeType` 做白名单校验，
不能依赖接口报错——否则口径错了也毫无征兆。

## 网页导出路线补不了历史数据（2026-07-29 实测）

同时排入 07-25 至 07-28 四个 `order_items` 补数任务，结果：

| 业务日 | 结果 |
|---|---|
| 07-28（昨天） | 成功 |
| 07-27 | 失败 `KUAIMAI_TIME_RANGE_NOT_APPLIED` |
| 07-26 | 失败 `WEB_COLLECTION_BUSINESS_DATE_MISMATCH` |
| 07-25 | 失败 `KUAIMAI_TIME_RANGE_NOT_APPLIED` |

**只有「昨天」能成功。**

### 根因：断言太早，读到的是上一天的筛选

排查中先后否掉三个猜测，都是在生产页面上实测否掉的：

1. ~~日期填不进去~~ — 采集器用的原生 setter + input/change/blur 写法有效，
   值留得住，且一直传到查询参数（实测填 07-23 后 URL 变为
   `startTime=1784736000000`，正是 07-23 00:00:00+08:00）
2. ~~URL 没带筛选参数~~ — `buildKuaimaiTaskUrl` 本来就带
   `timeType=created&startTime=&endTime=`，`route` 只是基址
3. ~~只改 hash 不重新查询~~ — 同标签页内改 hash 实测生效，输入框与记录数都更新

真正的原因是时机。页面「就绪」的判据是**控件存在**，而补数任务连着跑会复用
同一个标签页、只换 hash——控件本来就在，只是还带着上一天的值。
`verify_time_range` 是动作清单的第一步且立刻断言，于是读到旧筛选就抛
`KUAIMAI_TIME_RANGE_NOT_APPLIED`。

这同时解释了两件事：为什么「昨天」总能成功（当天第一次跑是新开标签页，
控件和正确的值一起出现），以及 07-26 为什么是
`WEB_COLLECTION_BUSINESS_DATE_MISMATCH`（断言在值切换的间隙侥幸通过，
导出的却是别的日期）。

修法是等值追上来再判定，而不是立刻判定。

## 行数据结构与字段映射（已实测）

`/trade/search` 的 `data.list` 是订单数组，子表在 `orders`。

| 目标列 | 来源 | 说明 |
|---|---|---|
| 系统订单号 | `sid` | 单日 200 行样本内唯一 |
| 平台订单号 | `tid` | |
| 内部单号 | `shortId` | |
| 平台 | `shopSourceName` | `source` 为 fxg/pdd/tm/kuaishou/jd/xhs/sys |
| 店铺 | `shopName` | |
| 商品数量 | `Σ orders[].num` | **主表没有数量字段** |
| 订单买家已付金额 | `payment` | |
| 订单成本 | `Σ orders[].cost × num` | 见下 |
| 下单时间 | `created` | 毫秒时间戳 |
| 条码 | `orders[].outerId` | 69 码 |

**`cost` 是单价成本，不是整行成本。** 同一条码在 `num=1/2/3/4` 下 `cost` 恒定
（实测 3、6.5、7.5、13 四组）。直接累加会把多件商品的成本按一件算，
严重低估成本、虚高毛利。

映射在 2026-07-25 的 200 行真实数据上验证：业务日全部为 07-25，系统订单号
全唯一，69 码合规 199/200，数量与成本无零值，合计 328 件、已付 ¥4,561、
成本 ¥1,984（毛利率 56%）。

## 时间基准：下单时间就是订单创建时间

订单查询页的时间基准选项里**没有「创建时间」**，第一项是「下单时间」。
实测切到「下单时间」查 07-25：URL 参数变为 `timeType=created`，页面返回
**6955 条**，与接口 `created` 口径完全一致（付款时间口径为 6556）。

因此采集器配置的 `timeBasis: "下单时间"` 符合 PRODUCT.md 的订单创建时间口径，
无需修改。销售报表页则另有「创建时间」选项，配置用的就是它。
