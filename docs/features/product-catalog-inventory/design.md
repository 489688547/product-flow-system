# 商品主数据库存与日期经营视图设计

## 设计结论

采用“扩展现有商品目录读模型”方案。`/api/platform/v1/product-catalog` 在服务端读取商品目录、所选日期段销售事实和最新可信库存事实，完成确定性归属后一次返回。页面不并行请求商品目录与货流库存，也不新建只服务于一个页面的聚合 API。

## 信息架构

页面保持商品治理工作台的三层结构：

1. 状态摘要：商品总数、当前日期段有销量商品数、销售未匹配数、库存待匹配数和来源日期。
2. 表格工具栏：左侧保留任务视图与本地搜索；右侧显示平台和日期段。
3. 商品表：商品、SKU/69 码、分类/品牌、销量/净销售额、成本、库存和状态/操作。

库存列固定放在成本列之后。库存不是日期段指标，列标题或工具提示需注明“最新快照”，避免用户误认为库存也按历史日期计算。

## 日期交互

- 预设日期选择后立即形成完整范围并自动应用。
- 自定义日期只有起止日期都合法时自动应用；输入中间态不发请求。
- 平台选择沿用现有经营筛选，并与当前日期段组成一次查询。
- 自动应用时保留上次成功数据，在工具栏显示“经营数据更新中”，不使用整页骨架清空表格。
- 请求使用递增请求标识或 `AbortController`；旧日期请求晚返回时必须被丢弃。
- 查询成功后分页回到第一页，已有本地搜索与任务视图继续作用于新结果。

## 库存读模型

服务端分三步构建库存：

1. 读取货流库存质量摘要，确定最新完整可信快照日期。
2. 只读取该快照的必要字段，并建立真实 `productId`、`skuId`、SKU 编码和 69 码的无歧义索引。
3. 按商品类型计算单品全仓合计或组合品可组套数量，并输出覆盖状态。

库存聚合使用纯领域函数，路由只负责认证、业务数据库选择、查询和响应。领域函数不依赖 D1、React 或浏览器。

### 单品

- 对目录中的每个 SKU 找到唯一库存单位。
- 同一库存单位的多仓 `calibratedQuantity` 相加。
- 多个目录 SKU 的库存相加为商品库存。
- SKU 无映射或映射冲突时，商品库存进入 `unmatched` 或 `incomplete`。

### 组合品

- 只使用商品目录中已确认的 `components` 与正数用量。
- 每个组件先按单品规则计算可用校准库存。
- 组合库存为各组件 `FLOOR(库存 / 用量)` 的最小值。
- 任一组件缺失或冲突时不返回部分计算值。

## 展示规则

| 状态 | 主值 | 辅助信息 |
| --- | --- | --- |
| `available` | 数量 | `最新快照 YYYY-MM-DD` |
| `zero` | `0` | `已匹配，当前无库存` |
| `unmatched` | `—` | `库存待匹配` |
| `incomplete` | `—` | `组件或 SKU 关系不完整` |
| `unavailable` | `—` | `库存暂不可用` |

数量右对齐并使用 tabular numbers。组合品可增加“最多可组 N 套”文字，但不增加第二个库存数字。状态必须同时使用文本和图标，不只依赖颜色。

## 页面状态

- 初次加载：摘要和表格骨架。
- 经营刷新：保留目录和库存，只给销售列及日期工具栏显示更新状态。
- 库存不可用：商品和销售正常显示，库存列逐行显示不可用；页面顶部显示一个可重试提示。
- 部分待匹配：表格正常展示，摘要显示待匹配商品数；不把数据质量问题扩大为全页错误。
- 空目录：沿用现有商品同步/导入引导。
- 无筛选结果：保留筛选条件并提供清除入口。
- 无写权限：目录、销售和库存可读；现有导入动作保持隐藏或禁用。

## 响应式与无障碍

- 工具栏在桌面端右对齐日期段；640px 以下换行，390px 下日期起止输入纵向排列。
- 表格设置稳定最小宽度，仅表格容器横向滚动，页面本身不产生横向滚动。
- 日期、平台、库存状态均有可见标签或 accessible name。
- 日期错误使用 `role="alert"`；加载状态使用 `aria-live="polite"`。
- 所有交互保留 `focus-visible`；日期弹层支持 Esc 关闭并把焦点归还触发器。

## API 与兼容

- 扩展 `GET /api/platform/v1/product-catalog`，不新增路由。
- 复用现有身份、部门权限和 `businessDatabase(context)`；不直接读取固定 D1 binding。
- 新增响应字段向后兼容；不带日期参数的旧客户端仍可获得目录，并可获得最新库存摘要而不扫描销售表。
- 库存查询失败应返回结构化部分可用状态或安全错误，具体策略在实施计划中以现有 API 错误契约为准，不能静默返回全零。
- API 文档、认证、权限、响应、错误、可观测性和回滚写入 `docs/platform/apis/product-catalog-v1.md`。

## 共享能力评审

结论：扩展现有共享能力。

- 商品目录已经被数据中心、产品全周期和供应链消费，库存是同一商品读模型的当前经营事实。
- 货流库存继续是唯一库存事实；商品目录只做可复用的商品归属和摘要，不复制事实。
- 销售继续是唯一日需求事实；日期段只影响销售聚合。
- 组合库存计算放在共享领域边界，可供后续补货、清仓和商品详情复用。

## 性能与容量

- 先定位一个最新完整快照，再读取该快照必要字段；不扫描全部历史库存。
- API 服务端聚合，不向浏览器返回 3,000+ 仓库明细。
- 商品目录、销售和库存查询可并行读取，但必须在同一业务数据库与同一请求权限上下文中完成。
- 目标是在当前生产规模下保持单请求可用；实施计划需增加有界查询和生产冷/热请求验收。

## 验证范围

- 领域：单品多仓合计、多个 SKU、组合配比、缺组件、重复编码、零库存和未知库存。
- API：认证、部门裁剪、业务数据库路由、库存质量、日期上限、兼容旧请求和安全错误。
- UI：日期自动刷新、竞态、库存列顺序、加载保留、空/错误/禁用、键盘和响应式。
- 生产：开发站先验证真实目录和库存快照，再经 `dev → main` 发布；生产验收检查 commit、OAuth、冷/热请求和真实商品数量，不输出商品明细。
