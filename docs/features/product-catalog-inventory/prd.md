## 背景与问题

商品主数据已经展示商品、SKU、69 码、分类、品牌、所选日期段销量、净销售额和成本，但用户无法在同一行确认当前可用库存。判断补货、清仓或活动承接能力时，需要另行打开供应链库存页面并手工按商品、SKU 和组合关系核对。

页面已有日期和平台查询草稿，只有点击“查询数据”才更新销量和净销售额。用户已确认日期段应放在表格右上角，并在确认合法日期后自动刷新经营数据，不再要求额外点击查询。库存属于最新可信当前快照，不受历史销售日期段影响。

## 目标

1. 在商品主数据的成本列后增加库存列，显示最新可信校准库存。
2. 普通商品按确定性 SKU 关系汇总所有仓库的校准库存。
3. 组合商品按正式组件关系和配比计算最多可组套数量。
4. 把日期段放到表格右上角；合法日期确认后自动刷新销量和净销售额。
5. 由共享商品目录 API 一次返回商品、销售和库存读模型，前端不并行拼装两套事实。
6. 对缺失商品映射、缺失组件关系、快照不可信或覆盖不足显示明确未知状态，不把未知补成零。

## 非目标

- 不新增 D1 表，不复制 `goods_flow_inventory_daily` 或 `product_sales_daily`。
- 不按历史日期回放库存；库存始终取最新完整可信快照。
- 不修改快麦 ERP、仓库库存或商品档案。
- 不把商品主数据改造成仓库级库存明细页或库存分析驾驶舱。
- 不从商品名称、编码长度或编码前缀猜测 SKU、组合类型或组件关系。

## 用户与权限

- 已登录且具备商品目录读取权限的员工可查看库存数量和库存状态。
- 库存数量不属于采购金额；成本及库存金额仍沿用服务端部门裁剪，前端不得推导被隐藏金额。
- 总经办与运营部继续拥有现有商品导入能力；本功能不扩大写权限。
- 服务端执行权限和数据环境选择；前端隐藏列或按钮不构成授权边界。

## 用户流程

1. 用户进入“数据中心 → 商品主数据”，在表格右上角看到平台和日期段。
2. 用户选择预设日期，或填写完整的自定义起止日期。
3. 日期合法后页面自动应用查询，保留上次成功表格并显示“经营数据更新中”。
4. 销量和净销售额按新日期段更新；库存继续显示最新可信快照，不随日期变化。
5. 用户在成本列后查看库存。库存待匹配时可打开商品详情核对 SKU、69 码或组合关系。

## 业务规则

1. 销售使用订单创建时间、`Asia/Shanghai` 和闭区间日期；默认排除“其它/其他/未知”平台。
2. 默认日期范围沿用现有商品主数据规则；预设或完整自定义日期确认后自动查询，最长 370 天。
3. 自定义日期只填一端、起始日晚于结束日或超过 370 天时不发请求，并就地显示错误。
4. 单品库存使用最新完整可信库存快照的 `calibratedQuantity`；相同 SKU 在多个仓库的数量相加。
5. 单品优先通过真实 `productId` 归属；缺少商品 ID 时，只允许用无歧义的 `skuId` 或已登记 SKU/69 码匹配，不从仓库或名称构造商品 ID。
6. 组合商品库存等于所有组件可组套数量的最小值：`MIN(FLOOR(组件校准库存 / 组件用量))`。
7. 任一必需组件缺失、组件用量无效、映射不唯一或快照不完整时，组合库存为未知并显示“库存待匹配”，不得只用已匹配组件计算。
8. 已确定性匹配且数量确实为零时显示 `0`；未知、无权限或缺少可信快照显示 `—` 和原因。
9. 库存元数据必须返回快照日期、覆盖率、可信等级和匹配状态；页面不得把接口响应时间当作库存日期。
10. 商品目录、销售和库存任一子来源失败时，API 返回安全错误或明确部分可用状态；前端保留最近成功结果，不把失败数据覆盖为零。

## 数据定义

- `inventory.quantity`：商品最新可信校准库存；单品为全仓合计，组合品为可组套数量。
- `inventory.status`：`available`、`zero`、`unmatched`、`incomplete`、`unavailable`。
- `inventory.snapshotDate`：被消费的完整库存快照业务日期。
- `inventory.coverage`：该商品所需 SKU/组件的确定性匹配覆盖率，范围 `0–1`。
- `inventory.confidence`：来源库存质量等级；沿用货流事实返回值，不在商品目录重定义。
- `inventory.matchedSkuCount`：实际参与单品库存合计的目录 SKU 数量。
- `inventory.requiredComponentCount`：组合商品所需组件数量。
- `inventory.matchedComponentCount`：组合商品已确定性匹配的组件数量。
- `sales.quantity`：所选日期和平台内销量。
- `sales.netSales`：所选日期和平台内净销售额。

## API 契约方向

扩展现有：

```http
GET /api/platform/v1/product-catalog?from=YYYY-MM-DD&to=YYYY-MM-DD&platform=<平台>
```

每个商品在已有 `sales` 之外增加：

```json
{
  "inventory": {
    "quantity": 128,
    "status": "available",
    "snapshotDate": "2026-07-28",
    "coverage": 1,
    "confidence": "trusted",
    "matchedSkuCount": 3,
    "requiredComponentCount": 0,
    "matchedComponentCount": 0
  }
}
```

`meta.inventory` 返回快照日期、库存质量状态、总行数、仓库数、SKU 数、商品覆盖数、待匹配商品数和来源更新时间。旧客户端忽略新增字段即可，不改变现有参数、认证或权限。

## 异常与边界

- 无完整库存快照：目录和销售仍可返回，所有库存为 `unavailable`，页面显示“库存暂不可用”。
- 快照质量非可信：不展示可决策数量，保留质量原因和快照日期。
- 商品无 SKU：库存为 `unmatched`，不显示 0。
- 同一编码归属多个商品：相关商品均为 `unmatched`，不重复分摊库存。
- 组合品没有正式组件：库存为 `incomplete`，不从商品名称推断组件。
- 日期查询失败：保留上次成功销量和销售额，日期控件显示失败并可重试；库存不清空。
- 库存读取失败：保留商品和销售，库存列显示不可用；服务端返回稳定错误和 request ID。

## 验收标准

1. 商品表列顺序为“销量 / 净销售额 → 成本 → 库存 → 状态/操作”，库存紧邻成本。
2. 普通商品的库存等于最新可信快照中其确定性 SKU 在所有仓库的校准库存之和。
3. 组合商品按正式组件比例返回最多可组套数量；缺任一组件时显示“库存待匹配”。
4. 日期段位于表格右上角；合法预设和完整自定义范围确认后自动刷新销量与净销售额。
5. 日期变化不改变库存快照日期或库存数量。
6. 0、未知、无权限、覆盖不足和接口失败具有不同文本状态，未知不得显示为 0。
7. API 一次返回目录、销售和库存，前端不直接调用货流库存 API 拼接。
8. 加载期间保留上次成功表格，旧请求结果不得覆盖更新日期段后的新请求。
9. 1280px、900px、640px 和 390px 下页面无横向溢出；表格只在自身容器滚动。
10. 键盘、焦点、加载、空、错误、禁用和钉钉 WebView 状态均可用。

## 上线与回滚

- 不新增迁移、环境变量或绑定；复用所选业务数据库中的商品目录、销售事实和货流库存事实。
- 服务端库存聚合必须有有界查询和契约测试；不得把全量仓库明细下发浏览器后聚合。
- 回滚时移除商品目录响应中的 `inventory` 和页面库存列即可，原始商品、销售和库存事实不变。
- 生产交付遵循 `codex/* → dev → main` GitOps 流程；开发站验收通过前不发布生产。
