## 背景与问题

项目的开发、部署和调试经验目前散落在对话、个人记忆和不同文档中。已经解决的问题可能被下一位开发者重复调查；多人分别记录相似结论后，也可能出现重复、冲突或过期指导。团队已经确认采用 EveryInc Compound Engineering 的知识沉淀和刷新流程，但所有 Fork 必须获得一致版本，且上游更新不能直接改变项目工作方式。

## 目标

- Fork 仓库后直接发现并使用 `ce-compound` 和 `ce-compound-refresh`，无需个人安装。
- 只把已验证、非简单且可复用的问题沉淀到 `docs/solutions/`。
- 用结构化刷新流程处理重复、冲突、过期和证据不足的经验。
- 固定 EveryInc 正式版本，保留来源、提交和 MIT 许可证。
- 上游升级只创建面向 `dev` 的独立 PR，经过项目完整 CI 和人工评审后生效。

## 非目标

- 不引入 EveryInc 的全部规划、开发、提交或 PR 自动化 Skill。
- 不自动合并上游更新，不执行未评审的上游脚本。
- 不把聊天记录、Token、Cookie、Provider 原始响应或生产秘密写入经验文档。
- 不让经验文档覆盖 `PRODUCT.md`、`DESIGN.md`、`AGENTS.md`、平台文档、ADR、当前代码或测试。

## 用户与权限

- 所有核心开发者均可在自己的功能分支运行两个 Skill，并提交经验文档。
- 经验与 Skill 更新通过现有 GitHub PR 权限和代码评审治理。
- GitHub Actions 只能创建升级分支和 PR，无权直接合并到 `dev` 或 `main`。

## 当前流程

1. 开发者解决问题并在对话或个人笔记中记录。
2. 后续开发者依赖关键词和个人记忆寻找旧结论。
3. 冲突经验通常由最后修改者人工覆盖，缺少统一证据门槛。

## 目标流程

1. 完成非简单问题并取得验证证据。
2. `verification` 在交付前触发 `ce-compound`，检查重复并写入 `docs/solutions/`。
3. 重大重构、矛盾或过期迹象触发 `ce-compound-refresh`。
4. 刷新流程执行保留、更新、合并、替换、删除之一；证据不足时标记 `stale`。
5. 每周检查 EveryInc 正式版本；发现更新时创建升级 PR，等待 CI 和人工评审。

## 业务规则

- 经验可信度优先级：当前代码与测试 > 产品、设计、平台和 ADR > `AGENTS.md` > 已验证经验 > `stale` 经验。
- 未解决、未验证、机械性修改和一次性猜测不得沉淀。
- 同一问题高度重叠时更新规范文档，不保留两个会漂移的权威结论。
- 自动升级只复制明确允许的两个 Skill 和许可证，不执行上游内容。
- 每次升级必须固定 tag 和完整 commit SHA；禁止跟随浮动 `main`。

## 数据定义

- 上游清单：仓库 URL、正式 tag、完整 commit、许可证和允许同步的 Skill 列表。
- 经验文档：EveryInc 定义的结构化 frontmatter 与正文，存放在 `docs/solutions/<category>/`。
- 本功能不新增数据库、环境变量或生产数据。

## 异常与边界

- 上游 tag 不存在、commit 不符、目录缺失、包含符号链接或复制越界时，同步失败且不修改现有 Skill。
- GitHub 禁止 Actions 创建 PR 时，工作流明确失败位置，不直接推送 `dev`。
- 新旧经验冲突但证据不足时保留原文并标记 `stale`，不自动选边。
- Skill 与项目强制规则冲突时，项目规则优先。

## 验收标准

1. 新 Fork 中存在完整的两个 Skill、固定版本清单和 MIT 许可证。
2. 验证流程明确要求在产生可复用经验时运行 `ce-compound`。
3. 真实 ECS 事故可以生成结构化 `docs/solutions/` 文档，且不包含秘密。
4. 冲突场景会进入合并、替换或 `stale`，不会最后写入者直接覆盖。
5. 上游检查工作流只向 `dev` 创建升级 PR，且 PR 带齐仓库治理声明。
6. 同步脚本和治理检查对非法来源、漂移版本、缺文件和符号链接失败关闭。

## 上线与回滚

本功能仅改变仓库内开发工具和文档，不部署生产运行时。回滚时恢复前一提交即可；`docs/solutions/` 保留在 Git 历史中。上游升级逐 PR 回滚，不影响产品数据与 ECS 服务。
