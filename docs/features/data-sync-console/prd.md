# 数据同步控制台 PRD

## 文档状态

- 状态：待评审
- 负责人：数据中心
- 最近更新：2026-07-27

本特性取代 `data-warning-recovery` 在数据同步页的呈现方式，把该页从「一个异常 + 一个按钮」重排为
可查看覆盖情况、批量补数的控制台。`data-warning-recovery` 定义的处置指引口径继续沿用，
但不再以单日异常卡的形式呈现。

## 背景与问题

数据总览显示 07-25 完全没有柱子、07-26 与 07-27 只有一小截，但右上角只提示「7 月 27 日数据疑似不完整」，
进入数据同步后也只能重新采集 27 日。

根因有两层：

1. `detectLatestSalesAnomaly` 取 `facts.at(-1)`，**按设计只检查最新一天**。更早的残缺日不会被检查。
2. `latestDailyFacts` 只收有数据的日期，**整天缺失的业务日不在数组里**，因此不存在「断档」这一异常类型；
   系统不认为它异常，只认为它不存在。

其次，残缺日会进入基线中位数并把它拉低，使后一天显得不那么异常，连续多日损坏时检测灵敏度下降。

页面层面还缺三件事：没有跨 Provider 的统一覆盖视图；无法多选补数；补数前不知道哪些平台需要登录，
经常排了队才发现要人工登录。

## 这个页面为谁创造什么价值

用户不是来管理采集任务的。他在数据总览看到某个数字缺了一块，过来问一句话：
**我的经营数据现在能不能信？不能信的话缺什么、我要做什么、什么时候好。**

现有页面按采集基础设施组织——采集器、任务、资源类型、归档目录——用户需要自己把
「`order_items` 采集失败」翻译成「我的销售额不能信」。本特性把这层翻译交给页面完成。

价值判定标准：进入页面 5 秒内知道数据能不能信；不能信时再一次点击即可开始补救，
或明确知道该去登录哪个平台。

## 影响范围必须区分

快麦 ERP 覆盖所有平台的订单，抖店等平台只覆盖本平台的经营指标。总览「平台分布」中
六个平台的 GMV 全部来自快麦 ERP。因此：

- **快麦缺一天**：净销售额、销量、毛利、退款率、平台分布全部失真。
- **抖店缺一天**：仅影响抖音的流量与内容分析，销售数字不受影响。

两类缺口严重性相差一个数量级。页面必须分别陈述，不得并列成同等的「采集失败」。

## 目标

- 在一个表里看到最近若干业务日、各 Provider 各资源的同步覆盖情况与状态。
- 识别三类问题：整日断档、当日残缺、任务失败或等待人工。
- 支持多选补数与「一键补齐全部失败」，提交前弹窗确认将要采集的清单。
- 弹窗明确列出每个平台的登录与连接状态，让用户在排队前就知道哪些需要先登录。
- 明确告知采集串行执行，避免用户误以为多选会并行加速。
- 排队之后能随时看到进度：当前在采哪个业务日的哪个资源、处于哪个阶段、队列里还剩几个。
  网页与 Chrome 扩展都要能回答「现在到底在干什么」，不需要用户去猜或去翻执行记录。

- 数据同步页每个区块只回答一个问题，不再出现多个区块重复回答「哪里出了问题」。

## 非目标

- 不改变 Chrome 负责页面动作与下载、本机服务负责等待与入库的拆分。
- 不删除任何既有能力。销售异常卡与抖店采集表被覆盖表和采集状态区取代，但其定位、处置指引、
  逐行重试与登录入口全部有明确去向，见设计文档的能力去向表。
- 不改动执行记录、快麦原始归档、待处理数据问题三个区块的内部结构，仅调整顺序。
- 不新增 Provider、资源类型或页面选择器。
- 不改变销售事实的订单创建时间、Asia/Shanghai 时区与截止昨天口径。
- 不引入并行采集。执行侧仍是单台公司 Mac 串行处理，本次只让这一约束可见。
- 不做自动登录或验证码自动处理。

## 用户与权限

- 具有数据中心查看权限的用户可以查看覆盖表、状态与登录提示。
- 只有具备采集触发权限的用户可以多选补数与一键补齐，权限判定沿用 `authorizeWebCollectionTrigger`。
- 服务端仍然独立校验权限，隐藏按钮不作为授权边界。

## 当前流程

1. 数据总览检测最新一天，异常时显示提示。
2. 点击进入数据同步，定位到该异常卡。
3. 卡片提供「重新触发」，目标日期固定为该异常日。
4. 更早的断档或残缺日没有任何入口，只能走导入官方报表或 `待导入` 文件夹。

## 目标流程

1. 进入数据同步，覆盖表默认展示最近 14 个业务日 × 已登记资源的状态。
2. 用户勾选若干有问题的行，或点击「补齐全部失败」自动勾选窗口内所有问题行。
3. 弹窗列出将要采集的清单（按平台分组、按业务日排序），并逐平台显示登录与连接状态。
4. 存在需要人工登录的平台时，弹窗给出该平台的登录入口，用户可选择「仍然排队」或先去登录。
5. 确认后任务进入队列，表内对应行显示队列位置；采集器串行处理，完成后状态自动更新。

## 业务规则

- 覆盖表的一行是一个采集目标：Provider + 资源类型 + 业务日期（抖店另含店铺）。与 `web_collection_jobs`
  的幂等键口径一致，不新增标识体系。
- 状态取值：已同步、残缺、断档、失败、等待人工、排队中、采集中、未登记。
- 断档判定：该业务日既没有任何采集任务，也没有对应的销售事实。
- 残缺判定：该业务日有销售事实，但相对同窗口内已判定健康日的中位数低于阈值。已判定为残缺或断档的日期
  不参与中位数计算，避免自我污染。
- 一次提交的补数目标数量有上限，超出时不提交并说明原因。上限是产品约束而非技术限制，用于避免一次排入
  远超单机当日处理能力的任务。
- 补数使用既有的强制重触发语义：`waiting_human`、`failed`、`schema_changed`、`success` 可重排；
  `queued` 不可重排，界面必须显示它已在队列中而不是伪装成一次新触发。
- 登录状态只读展示，不代表用户操作。系统不得声称已登录，只能报告最近一次采集观察到的结果。
- 进度展示只描述已经发生的事实：当前任务的阶段、队列中剩余数量、最近一次心跳时间。
  不估算剩余时间——单机串行且随时可能停在等待人工登录，任何时间承诺都会失真。
- 队列进度以服务端 `queued` 集合为准。Chrome 扩展一次只知道自己手上的任务，
  因此扩展只展示当前任务，不展示队列总数，避免给出以偏概全的数字。

## 数据定义

- 覆盖窗口：默认最近 14 个业务日，随数据总览的日期范围联动，上限 60 天。
- 队列位置：按 `business_date, created_at` 排序在当前 `queued` 集合中的序号，与领取顺序一致。
- 登录状态来源：采集器 `chrome_status`、店铺连接状态，以及最近任务的 `error_code`
  （`*_LOGIN_REQUIRED`、`*_HUMAN_VERIFICATION_REQUIRED`）。不读取也不展示任何凭据。

## 异常与边界

- 采集器离线：覆盖表照常展示，补数按钮可用但弹窗必须声明当前无设备领取，任务会排队等待。
- 单台采集器串行：弹窗显示「共 N 个任务，将依次执行」，不给出虚假的完成时间承诺。
- 窗口内全部健康：表格显示健康态，不构造伪造的问题行。
- 权限不足：只展示状态，不显示补数入口；服务端仍然拒绝越权请求。
- 覆盖窗口超过上限：拒绝并提示收窄范围，不静默截断。

## 验收标准

- 07-25 整日无数据时，覆盖表将其显示为断档并可被选中补数。
- 07-26 残缺时，覆盖表显示残缺，且该日不参与残缺判定的中位数计算。
- 多选提交后，弹窗按平台分组列出清单与登录状态，取消则不产生任何任务。
- 「补齐全部失败」只勾选窗口内的问题行，不含已同步行。
- 提交后队列中的行显示队列位置，且 `queued` 行的重复提交不伪装成新触发。
- 采集器离线时弹窗明确说明没有设备会领取。
- 超过单次上限时提交被拒绝并说明原因。
- 有任务在执行时，采集状态区显示当前业务日、资源、阶段与队列剩余数量，并随轮询更新。
- 重排后页面不再有两个区块回答同一问题：销售异常卡与抖店采集表不再存在，其能力可在
  覆盖表与采集状态区找到对应入口。
- 数据总览的「去处理」在多日问题时定位到覆盖表，单日时仍能直接看到该日所在行。
- Chrome 扩展弹窗在采集中显示业务日期与阶段，不再只显示平台与资源。
- 队列清空后进度条显示最近一次完成结果，不留下停在中途的假象。

## 上线与回滚

- 覆盖表与批量补数为新增能力，不改动既有异常卡与执行记录，可独立回滚。
- 检测逻辑变更影响数据总览右上角提示；回滚即恢复只检查最新一天的行为。
- 不涉及数据库结构变更，不需要迁移。
