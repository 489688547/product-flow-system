# 数据同步控制台 设计

## 用户来这个页面要什么

用户不是来管理采集任务的。他在数据总览看到某个数字缺了一块或者不对劲，于是过来问一句话：

> 我的经营数据现在能不能信？不能信的话缺什么、我要做什么、什么时候好。

页面的全部设计围绕这一句展开。凡是不服务于这句话的信息，都不放在主视线上。

现有页面按采集基础设施组织——采集器、任务、资源类型、归档目录——用户要在脑子里
把「`order_items` 采集失败」翻译成「我的销售额不能信」。这层翻译应该由页面完成，而不是由用户完成。

## 两种口径，不是主数据与辅助数据

| | 快麦 ERP | 平台自采（抖店，以及未来的拼多多、天猫、快手、小红书、京东） |
|---|---|---|
| 采什么 | 订单、订单明细、销售明细、商品、库存 | 店铺每日、商品每日、直播每日、短视频每日 |
| 覆盖范围 | 所有平台的订单 | 只有本平台 |
| 口径 | **公司统一口径**，为在多个电商平台之间可比而做过归一 | **平台官方口径**，与该平台后台显示一致 |
| 权威于 | 跨平台比较、公司总账、平台分布 | 与平台对账、平台侧运营与内容分析 |

关键事实：**快麦里的抖音销售数字与抖店后台显示的数字本来就不一样**，因为快麦要平衡多个平台的
口径差异。这不是数据错误，两个数都对，各自回答不同的问题。

由此得出两条设计约束：

1. 页面**不得暗示两者应当相等**，也不得把其中一个标为「正确值」。任何同时出现两种口径的地方
   都必须标明口径来源。
2. 缺口的影响必须按口径陈述，而不是按「核心/辅助」陈述：
   - 快麦缺一天 → 公司统一口径的销售数字不能信，总览核心数字与平台分布失真。
   - 抖店缺一天 → 抖音官方口径的数字不能信，影响与平台对账和抖音侧运营分析；
     公司统一口径的销售数字**不受影响**。

总览页「平台分布」的六个平台 GMV 全部来自快麦 ERP 的统一口径，不是各平台自采的官方口径。

## 页面结构

```
数据同步
├── 结论条    我的数据现在能不能信
├── 同步覆盖  哪几天不能信、影响什么、怎么补
├── 执行记录  每一次跑了什么、结果如何
└── 本机原始归档  公司 Mac 上有哪些原始文件
```

「待处理数据问题」区块**删除**。它渲染 `state.qualityIssues`，该集合由供应链质量导入写入
（`QualityWorkspace.jsx`），装的是差评、抽检、整改这类商品质量事件，列头是「问题 / 类型 /
负责人 / 状态」。这是供应链的数据，出现在数据同步页属于错位，且长期为空。
真正的同步问题由覆盖表回答。供应链质量工作区不受影响。

原「销售异常卡」与「抖店 Chrome 官方报表采集」两个区块被结论条与覆盖表取代，能力去向见文末。

每个区块的副标题必须用一句话直说它回答什么问题，不写「统一管理…」「闭环处理…」这类
看不出用途的话。用户看不懂某块是干什么的，等同于该块不存在。

## 结论条

页面第一屏就给结论，不让用户自己从表里推。

```
⚠ 最近 14 天有 3 天的销售数据不能信          公司 Mac 采集器：在线 · 正在补 2026-07-25
```

- 健康时：`✅ 最近 14 天数据完整，截取到 2026-07-27`
- 只有平台经营数据缺口时：`✅ 销售数据完整 · 抖音经营数据缺 2 天`——**销售完整就先说完整**，
  因为那是用户最关心的数字。
- 有阻塞时结论条右侧给出动作入口：需要登录、采集器离线、导入官方报表。
- 正在采集时右侧显示当前业务日与阶段，队列剩余数量跟在其后。

## 同步覆盖

### 按业务日聚合，不按采集任务平铺

用户是从图表上某一天的缺口过来的，所以主键是**业务日期**，一天一行。

6 个平台 × 4 资源 × 14 天 = 336 个采集目标。平铺不可读，且随平台接入线性膨胀。
按业务日聚合后默认只显示有问题的天，通常 1–3 行。

### 行内容

```
2026-07-25   统一口径销售数据缺失                                   [补这天]
             影响 净销售额 · 销量 · 毛利 · 平台分布
             快麦 订单明细

             抖音官方口径数据缺失                                   [补这天]
             影响 与抖店对账 · 抖音流量与直播分析
             抖店 店铺每日/商品每日/直播每日/短视频每日

2026-07-26   统一口径销售数据不完整                                 [补这天]
             影响 净销售额 · 销量 · 毛利
             当日 ¥12,340，同期中位数 ¥128,000，约为 10%
             快麦 订单明细

2026-07-27   正在补齐 · 队列第 2 个                                  进度 →
             快麦 订单明细 · 正在下载报表
```

口径名出现在结论里而不是附注里。用户看到「统一口径」与「抖音官方口径」两个词，
才不会在别处发现两个数字不一致时误以为系统出错。

字段自上而下按「结论 → 影响 → 证据 → 技术明细」排列：

| 层 | 内容 | 为什么在这一层 |
|---|---|---|
| 结论 | 销售数据缺失 / 不完整 / 正在补齐 / 已补齐 | 用户第一眼要的答案 |
| 影响 | 受影响的业务指标名 | 把技术故障翻译成业务后果 |
| 证据 | 残缺时给当日值与同期中位数对比 | 让用户能自己判断「是真缺还是那天生意差」 |
| 技术明细 | 平台 + 资源类型 | 排查时才需要，不占主视线 |
| 动作 | 补这天 / 去登录 / 查看进度 | 每行只有一个主动作 |

「证据」这一层尤其重要：残缺判定是统计推断，可能误判。给出当日值与中位数，用户能一眼
看出 07-26 是真的缺数据还是那天真的只卖了这么多。系统不替用户下结论。

### 两种口径分行

同一天里，统一口径缺口与平台官方口径缺口分两行显示，因为它们回答不同的问题、处理优先级
也不同。统一口径行永远排在平台官方口径行之前——公司总账优先于单平台对账。

分行还有一个作用：让用户在页面上反复看到「两种口径」这件事，从而在别处发现快麦的抖音数字
与抖店后台不一致时，知道那是预期的，不是故障。

### 筛选与分页

- 默认只显示有问题的业务日。健康的天不占行。
- 「显示全部」开关可以看到窗口内所有业务日，用于确认某天确实已同步。
- 筛选：平台、口径（统一口径 / 平台官方口径）、状态。
- 展开某天可以看到该天下所有采集目标的逐条状态，供排查使用。
- 展开后的明细与「显示全部」列表都启用 `TablePagination`，与供应链各工作区一致。

### 多选与批量补数

- 勾选以业务日为单位。勾一天等于勾该天下所有问题目标。
- 「全部补齐」勾选当前筛选结果内的全部问题日。
- 正在补齐的天不可勾选，显示队列位置——强制重触发对 `queued` 状态无效，
  给一个不产生任何变化的按钮是欺骗。
- 提交前弹窗确认，见下节。

## 采集器离线时哪些信息不可信

页面上关于「能不能采」的判断全部来自采集器的上报：`chrome_status` 只在心跳时写入，
任务错误码是历史值。采集器离线时这些值不会更新，因此**不再代表当前状态**。

规则：**采集器离线时，扩展与登录状态一律显示为未知，并注明最近一次上报的时间与内容。**
不得把过期心跳渲染成「扩展已连接」。

| 信息 | 采集器在线 | 采集器离线 |
|---|---|---|
| 扩展连接状态 | 按 `chrome_status` 显示 | 「未知 · 最近于 07-25 02:46 报告为扩展已连接」 |
| 平台登录状态 | 按最近任务错误码显示 | 「未知 · 最近一次采集提示需要登录」，措辞为历史陈述 |
| 队列位置 | 显示 | 显示，但注明无设备领取 |
| 当前任务阶段 | 显示 | 不显示执行中，改为「队列中 N 个，等待采集器上线」 |
| 覆盖表的断档与残缺 | 可信 | **仍然可信**，它来自销售事实与任务记录，与采集器是否在线无关 |

最后一行是关键区分：**「数据缺不缺」与「现在能不能采」是两个独立问题**。采集器离线不影响
前者的准确性，只影响后者。页面不得因为采集器离线就把覆盖表整体标为不可信。

### 离线处置流程

补数前必须先确认采集器在不在线，而不是排完队再让用户自己发现没人干活。

1. **打开补数弹窗时强制刷新一次状态**，不使用页面缓存。在线判断必须是当下的，
   否则用户看到的可能是几分钟前的心跳。
2. **在线** → 正常清单，主按钮「确认排队」。
3. **离线** → 弹窗切换为阻塞态：
   - 顶部说明公司 Mac 采集器未上报心跳，当前没有设备会领取任务。
   - 给出处置指引：确认公司 Mac 已开机、采集器服务在运行、Chrome 已打开。
   - **主按钮变为「重新检测采集器」**，次按钮才是「仍然排队」。默认动作是去解决问题，
     不是往空队列里塞任务。
   - 明确告知排队后 24 小时仍无人领取会自动标记为失败，需要重新触发。
4. 「重新检测」重新拉取状态；恢复在线则弹窗就地切回正常态，不需要用户重开。

结论条在离线时同样把「重新检测采集器」作为主动作，与弹窗保持一致。

浏览器无法直接探测公司 Mac 上的采集器——本机服务只监听 `127.0.0.1`，线上页面够不着。
因此「重新检测」的语义是重新读取服务端心跳，而不是主动 ping。文案不得暗示是主动探测。

补数在离线时仍然允许，因为用户可能打算稍后启动采集器；但它必须是用户明确选择的次要路径。

## 确认弹窗

```
补数确认

将采集 6 个目标，覆盖 2 个业务日。采集器一次只处理一个，任务会依次执行。

统一口径销售数据（影响净销售额、销量、毛利、平台分布）
  快麦 · 扩展已连接
    订单明细   2026-07-25、2026-07-26

平台官方口径数据（影响与该平台对账及平台侧运营分析）
  抖店 · 需要登录 ⚠
    店铺每日、商品每日   2026-07-25（TIYES提野星宠物用品旗舰店）

⚠ 抖店最近一次采集提示需要登录，现在排队也会停在等待人工。
   [打开抖店登录页]

公司 Mac 采集器：在线
                                          [取消]  [确认排队]
```

- 按口径分组，统一口径在前，与覆盖表顺序一致。
- 每个平台一行连接与登录状态，需要登录的给出该平台登录入口。
- 采集器离线时把「在线」换成明确的离线说明，仍可确认——排队本身有效，只是没有设备会立刻领取。
- 不显示预计完成时间。单机串行且随时可能停在等待人工，任何时间承诺都会失真。

## 采集进度

进度是结论条的一部分，不单独成块——它回答的是「能不能信」的时间维度。

### 网页

```
公司 Mac 采集器：在线 · 正在补 2026-07-25 快麦 订单明细 · 正在下载报表 · 队列还剩 4 个
```

- 阶段文案复用 `stageText`，`stage` 落后于 `status` 时以 `status` 为准。
- 队列数量取服务端 `queued` 集合，与领取顺序同源。
- 采集器离线但队列非空时显示「队列中 N 个，等待采集器上线」，不显示虚假的执行中。
- 队列清空后显示最近一次结果并保留到下次采集开始，避免进度突然消失让人以为没跑过。
- 不显示预计剩余时间。使用 `role="status"` 播报阶段变化，不抢焦点。

### Chrome 扩展弹窗

`activeJob` 存的是完整任务对象，业务日期与阶段本来就在本地，只是没渲染。

```
● 正在采集
  快麦 · 订单明细
  2026-07-25 · 正在下载报表
```

只增加业务日期与阶段两行。**不显示队列总数**——扩展一次只领一个任务，
不知道服务端队列里还有多少，显示一个它无法保证的数字会误导。队列进度只在网页给。

## 数据总览的提示

总览页本身不重做，只改右上角健康提示，且必须区分影响范围。

| 情况 | 改为 |
|---|---|
| 销售数据 1 天有问题 | ⚠️ 7月27日销售数据不完整 · 去处理 |
| 销售数据多天有问题 | ⚠️ 3 天销售数据不完整 · 去处理 |
| 仅平台经营数据有问题 | ⚠️ 抖音经营数据缺 2 天 · 去处理 |
| 全部健康 | ✅ 数据截取到 2026-07-27 |

销售缺口优先于平台经营缺口展示。多日时不罗列具体日期，提示条宽度有限，具体哪几天进页面看。
计数口径与覆盖表一致，避免两个页面给出不同数字。

## 状态与焦点

- 加载中：结论条显示读取中，覆盖表骨架，动作按钮禁用。
- 空状态：没有问题日时显示「最近 14 天数据完整」，不构造伪造行。
- 错误：读取失败时结论条显示读取失败与重试入口，其余区块保持可用。
- 权限只读：不渲染勾选列与补数按钮，结论与状态照常展示。
- 焦点：弹窗打开时焦点进入弹窗，关闭后回到触发按钮；勾选支持键盘操作。
- 提交后焦点保留在工具条，通过 `role="status"` 播报「已排入 N 个任务」。

## 无障碍与响应式

- 勾选与展开控件有可读标签（业务日期 + 问题摘要），不靠视觉位置区分。
- 状态不能只靠颜色区分，徽章内始终有文字。
- 影响指标名用文字列出，不用图标代替。
- 笔记本宽度下保持表头单行，列宽不足时水平滚动；移动端与 WebView 下行内容纵向堆叠。
- 弹窗高度受限时内部滚动，操作按钮保持可见。对比度遵循 WCAG AA。

## 被取代区块的能力去向

| 原能力 | 去向 |
|---|---|
| 异常卡：定位最新异常日 | 覆盖表按业务日列出全部问题日 |
| 异常卡：处置指引与登录入口 | 结论条的阻塞提示与动作入口 |
| 异常卡：单日重新触发 | 覆盖表行内「补这天」 |
| 异常卡：导入官方报表入口 | 结论条保留该入口 |
| 抖店表：按店铺列出四类资源 | 覆盖表展开后的逐条明细，抖店行附店铺名 |
| 抖店表：逐行重新触发 | 覆盖表行内补数，且可多选 |
| 抖店表：打开抖店登录页 | 结论条与确认弹窗的登录入口 |
| 待处理数据问题 | 删除，属供应链质量数据错位 |

除「待处理数据问题」为有意删除外，没有能力被丢弃。

## 平台扩展

拼多多、天猫、快手、小红书、京东接入后：

- 覆盖表不新增区块，新平台作为平台经营数据行并入对应业务日。
- 结论条的销售结论不受影响——销售事实始终来自快麦 ERP 一个来源。
- 筛选器的平台选项由已登记 Provider 动态生成，不写死。
- 行数不随平台线性膨胀，因为默认只显示有问题的业务日，且同一天的同类缺口合并成一行。
