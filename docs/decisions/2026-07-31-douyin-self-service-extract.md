# 抖音日事实改由自助取数接口采集

## 状态

已实施，2026-07-31。

## 背景

抖音日事实原先靠逐页导出与页面标签抓取，有两个不能忍的问题。

一是**指标不可信**。店铺面板曾显示 314 万成交订单数、257 万成交人数，而同日 GMV 只有 6.5 万；
这两项已从面板撤下。罗盘首页接口不返回它们。

二是**页面驱动本身不可靠**。罗盘的日期控件只认可信事件，而 CDP 派发可信事件只能按视口坐标，
于是接连出现这几类故障，且**失败时都不报错，只是点空**：

- 量完坐标后元素仍在动画中，点 25 号点成了正上方的 18 号（差整整一行）；
- 日期面板展开在视口下方（视口高 1092，面板占 925~1218），坐标不在视口内，
  `elementFromPoint` 返回 null；
- 选完维度后粒度选项整组重绘，紧接着点粒度点在旧位置上，粒度没选中，
  而失败发生在两步之后的日期面板。

页面缩放不是 100%、平台改个 class 名，同样会挂。

## 决策

**改走罗盘自己的接口，页面表单驱动删除。**

```
GET  /data_factory/download/config      取该维度可选的粒度、指标分类与指标
POST /data_factory/download/submit      建任务（实测 286ms，驱动表单要三分钟）
GET  /data_factory/download/task_list   查任务（支持 task_name 精确过滤）
GET  /data_factory/download_file        取文件（列表直接给全地址）
```

请求一律在页面上下文里发，登录态与 CSRF 由专用浏览器自己带，**采集器不读、不存任何凭据**。
下载地址按端点放行（`download_file?task_id=<纯数字>`），白名单不放宽成模糊匹配。

### 指标：店铺与商品全选，直播与短视频只能选定

维护一份「我们要哪些指标」的清单本身就是脆弱点：漏选一类，那几列静默变成 null
（店铺少选退款与流量，面板的退款率与曝光点击率就没了，且不报错）；平台新增指标，
我们也不会知道。所以**店铺与商品一律全选**——实测店铺 6 类共 76 个指标全选接口照收，
身份列仍是「日期」/「商品ID」。落库只取登记过的列，其余留在归档文件里，将来要用不必重采。

**但直播与短视频不能全选。** 全选会把「基础信息」里的达人字段（`author_id`、`nickname` 等）
一并带上，于是**行的身份从直播间/短视频变成了达人**：preview 实测直播全选后列里根本没有
「直播间ID」，短视频没有「短视频ID」。那不是少一列，是整张表的含义变了。因此这两个维度
用选定集，基础信息只取 `live_start_ts`（业务日靠它归集）。

### 任务名必须编码「这次到底要什么」

平台按名称判重，而我们的名字是确定性的。名字若只有维度与区间，改了指标集之后重名逻辑
就会把旧任务当成「同一个请求」接着等——**实测中过一次：提交的是全选，下回来的却是旧的
10 列窄表，而且不报错**。同名 ≠ 同内容。名字因此带上一段指标集指纹（粒度、视频类型、
指标分类、指标）。平台的任务名上限是 40 字符，视频类型只留首字母。

### 口径按维度登记，不共用

四个维度的粒度、指标 value、指标分类编号、导出列名全都不同，任何一处套用店铺口径都会
静默出错。登记表与配置接口逐条核对，**提交前再核一次**——平台改了会当场说清是哪一项没了，
而不是排完队、下回一个少列的文件再由解析器报个离原因很远的错。

| 维度 | 粒度 | 分类 | 说明 |
|---|---|---|---|
| shop | `day` 自然日累计 | `1` 成交 | 唯一有「成交金额」`income_amt` 的维度 |
| product | `day` 自然日累计 | `1` 成交 | 只有用户支付金额 |
| live | `live_start_date` 开播日期累计 | `1`+`2` | 必须带 `live_start_ts`，见下 |
| video | `all` 统计日期累计 | `1`+`2` | 必须指定 `video_type`，只采挂车 |

**直播与短视频没有「成交金额」，只有「用户支付金额」。** 两者口径不同，不得混填。
短视频事实表因此补了 `user_payment_amount` 列（migration 0018）——没有这一列就只剩
丢数或冒充成交金额两条路，后者会造出看起来权威的错值。

### 业务日必须由数据自证

不靠「我请求的是这天」去推断：

- 店铺取「日期」列；
- 直播取「直播开始时间」——直播导出是一行一个直播间、只给区间统计日期，
  不取开播时间就会把 5 天当成 1 天，且落库后与真数长得一模一样；
- 短视频只能单日建任务，再由文件里的统计日期（`20260730-20260730`）自证；
  发布时间不能当业务日，5 月发的视频 7 月照样出单。

请求了哪几天就必须拿到哪几天，少一天整批不入库。

### 两道免费的提交前核对

每天只有 5 条配额（被拒绝的提交不占额度，但白建一条成功的任务就实打实少一条），
所以宁可多两次请求也不要建一条注定拿不到想要的列的任务：

1. **配置接口**核对粒度还在不在（指标全选的维度不必逐个核对；选定集的维度要核对）。
2. **preview 接口**核对列名。指标 key 还在，不代表导出的列名没变，而解析是按中文列名
   做的——列名一改，解析出来是一列静默的 null。preview 不建任务、不耗配额。

注意 preview 报的是**指标列**，不是导出文件的完整表头：实测直播的导出文件有
「直播间ID / 直播间名称 / 店铺名称」而 preview 里没有，反过来 preview 有「日期」而文件里
没有。店铺与商品两者恰好一致，所以这个差别是在直播上才暴露的。身份列因此不靠 preview
把关，而由入库时的必填校验拦下——别让一道检查假装管了两件事。

也正因如此，**列名一律以 preview 为准**，不拿配置接口的文案当列名：实测商品维度的
`refund_cnt`，配置说是「退款订单数（退款时间）」，preview 给的却是「（支付时间）」。

## 平台硬约束

- **每天只能建 5 条任务**，第 6 条直接被拒。额度在页面上不显示，只以接口拒绝的形式
  出现（`StatusCode 30000` /「每天仅支持创建5条任务」）。被拒绝的提交不占额度——
  实测当天两次被拒（重名、没选视频类型）都没计入，5 条是净成功数。
  四个资源各一条正好 4 条，只剩 1 条余量。规划阶段就挡住超配额的计划。
- **补历史**：店铺/商品/直播用「自然日累计 / 开播日期累计」拉长区间，一条任务就能覆盖
  很多天，14 个月切成 5 段正好是一天的配额。短视频例外——它只有区间合计粒度，要按天
  就得一天一条任务，每天最多补 5 天，14 个月补不动；若只要按月汇总则一条即可。
  单次区间上限尚未定论：preview 接受 425 天，而页面提示过「最长 3 个月」，
  代码仍按 92 天切段（保守），待用一次真实提交验证后再放宽。
- **平台先查配额再查重名**。崩溃重启后重跑收到的是「配额用尽」，而之前建的那条其实正在
  排队。两种拒绝都先回查任务是否已存在，在就接着等。
- 任务名是唯一的关联手段（列表只有名称、创建人、状态、创建日期），因此名字里必须带上
  维度、区间与视频类型。
- 状态码：`0` 排队中、`1` 取数中、`2` 取数完成。见过一次 `10`，但证据来自滞后的页面列表，
  不登记。失败码从未遇到。**未知码一律继续等并带上原始码**，下次遇到照此补映射。
- **不能拿 `download_url` 判断是否完成**：刚建好、排队 3/4 的任务同样带着下载地址。

## 切换范围：只切验证过的资源

走不走自助取数**由执行器按资源类型判定，不靠字段传输**。原先是在排日计划时打一个
`viaSelfService` 标记带过去，但 `web_collection_jobs` 表没有这一列，标记经服务端一个来回
就没了——执行器拿到 `undefined`，于是悄悄走回逐页导出。本地测试全绿，因为测试直接构造带
标记的任务，绕过了那个来回。「抖音日事实走自助取数」是资源的属性，不是某个任务的属性。

| 资源 | 走向 | 理由 |
|---|---|---|
| live_daily | 自助取数 | 覆盖逐页导出的全部，且多给可靠的成交订单数与成交人数 |
| video_daily | 自助取数 | 同上 |
| store_daily | 仍走逐页 | 自助取数这边目前只取成交类 7 项，缺结算金额、退款金额、商品曝光/点击人数——面板的退款率与曝光点击率正由它们算出。切过去那几项变成 null，两个比率就没了，且不报错 |
| product_daily | 仍走逐页 | 导出列名已实测（`统计日期 / 日期 / 商品ID / 商品名称 / 用户支付金额 / 成交订单数 / 成交人数 / 成交件数`），解析与入库映射已登记；但同样缺曝光/点击/退款，理由同 store |

store 与 product 要切，前置条件是：把结算/退款/流量三类指标也取上（配置接口可查其
指标 key），实跑一次并核对导出列名，再改 `SELF_SERVICE_RESOURCES`。

## 广告费

原先事实表里只有收进来的钱，答不了「广告费多少」，也算不了投放费比。指标全选后这些列
本来就在导出文件里，缺的只是落库的位置，因此补了六列（migration 0019）：

| 列名（以 preview 为准） | 字段 |
|---|---|
| 投放消耗（店铺被投） | `adCostAmount` |
| 支出金额（店铺被投） | `expenseAmount` |
| 平台佣金（财务已结算） | `platformCommission` |
| 达人佣金（财务已结算） | `influencerCommission` |
| 投放贡献成交金额 | `adContributedAmount` |
| 净成交金额 | `netTransactionAmount` |

**不落库平台自己的费比。** 它有「投放费比」「投放费比（剔除退款）」「综合费比」
「综合费比（剔除退款）」四个变体，口径不一；存一个说不清是哪种口径的比率，比不存更糟。
面板上的投放费比按 `投放消耗 / 成交金额` 现算，定义写在代码里。

## 成交订单数与成交人数何时能回面板

自助取数已经能给出可信值（实测 07-30 是 3265 单 / 2676 人），但库里既有的 `store_daily`
行来自页面抓取，正是显示过 314 万单 / 257 万人的那批。现在放回面板，面板会照旧把错值
显示出来。恢复的前提是先按 `source_version` 区分来源，或把历史回补掉。

## 即时通道：罗盘首页接口

自助取数排队 10-20 分钟且每天限 5 条，不适合「现在就想看昨天的数」。首页接口补上这一段：
秒级返回、不占配额、按天给数。

```
GET /compass_api/shop/common/homepage/core_index             经营概况
GET /compass_api/shop/common/homepage/summary_core_index_v3  收支概况（广告费在这）
参数：date_type=20、begin_date/end_date = `YYYY/MM/DD 00:00:00`
取值：data.module_data.<模块>.compass_general_multi_index_card_value.data[].<字段>.index_value.value
```

**为什么不是读页面上的数字。** 首页每张指标卡里挨着三个数：本店值、较上期、同行顶尖。
按标签就近找数字必然抓错——store_daily 曾因此显示 314 万成交订单数、257 万成交人数，
而同日 GMV 只有 6.5 万。在接口里这三者是 `value` / `last_value` / `benchmark`，各有其名，
不可能混淆。同一份数据，读法不同，可信度天差地别。

**只能用 `date_type=20`。** 实测 07-28：`21`（近7天）返回成交订单数 21382、`23`（近30天）
返回 97899，而那天真实约 3000——传单个日期只是锚定窗口末端，返回的是**窗口累计**。
拿它们「扩大可查范围」，落库的就是 7 天或 30 天合计冒充某一天。

**回溯窗口约 2 天**（实测 07-31 能取 07-30 与 07-29，07-28 就没有了）。更早的日期只能走
自助取数。取不到核心字段时整条不入库，不落一条全 null 的记录——那在页面上会显示成
「这天没生意」，比缺数更糟。

单位由接口显式给出（`3` 分、`4` 比率、`5` 计数），未登记的单位一律拒绝：把分当成元
差 100 倍，而 100 倍的错值看着仍像个正常数字。

三方交叉验证（2026-07-30）：首页接口、自助取数导出、页面截图三者的成交金额
¥65,449.76、成交订单数 3,265、成交人数 2,676 完全一致；广告费（投放消耗）¥13,116.02
与截图「¥1.31万」一致。

## 两条通道的分工

| | 首页接口 | 自助取数 |
|---|---|---|
| 速度 | 秒级 | 排队 10-20 分钟 |
| 配额 | 无 | 每天 5 条 |
| 回溯 | 约 2 天 | 14 个月 |
| 粒度 | 店铺整体 | 店铺 / 商品 / 直播 / 短视频 |
| 广告费 | 有 | 有 |

`store_daily` 在窗口内走首页、窗口外退回自助取数；其余三个资源只有自助取数一条路。
退回是显式判断（`withinHomepageWindow`），不是「试试看不行再说」——首页对超窗口的日期
不会报错，只会返回空值，硬取就会落一条全 null 的记录。

## 尚未摸清

首页下方还有「看流量 / 看商品 / 看搜索」几块，右上角也能自定义日期，都还没接入。
探测时用页内 fetch/XHR 拦截器没抓到它们的请求：这些模块的数据在首屏就已加载，
切换时间页签也没触发重取。下一步改用 CDP 的 Network 域抓——它不受页面导航与 SPA
缓存影响，比在页面里打补丁可靠。在摸清之前不猜接口路径：猜中的概率不高，
猜错了却可能拿到一个形状相似、口径不同的响应。

- `viaSelfService` 通道未接线时明确失败，不悄悄退回逐页导出——那条路采回的是另一个口径。
- 实测 07-30：店铺 GMV 65449.76 / 3265 单 / 2676 人；直播 196 场、支付 11551.77；
  短视频 2451 条、支付 29725.73 / 1692 单。
- 商品维度已实跑并验过：07-30 共 89 个商品，解析与入库映射登记完毕，
  只是尚未切换路由（缺曝光/点击/退款，理由同 store）。

## 历史数据：页面抓取那批整体不采信

库里 `commerce_store_daily_facts` 有 12 行来自 `douyin-store-capture-2026-07-24`
（罗盘首页的页面抓取），覆盖 07-23~07-30。逐行核对后发现三类问题：

| 现象 | 例子 |
|---|---|
| 数字被拼接 | 07-30 成交订单数存成 `3265840`（真值 3265，"3265" 接了相邻的 "840"）；07-29 存成 `3147743`（真值 3147）；07-30 成交金额存成 `65449.761`（真值 65449.76） |
| 同一天多行 | 07-24 两行、07-27 三行、07-28 两行 |
| 半成品 | 07-27 有两行 GMV 61400、成交订单数为空（采得太早） |

有几天看着是对的，但它们是同一套代码抓的，只是那天没撞上拼接。**没有任何规则能把
「看着对的」和「被拼接的」分开**——凭「看着合理」留一行，等于把没验证过的数字当真。
所以整个来源都不采信：宁可页面上缺这几天，也不要显示一个错的。缺数看得见，错数会被当真。

处理方式是**读取时过滤，不删数据**：`isDistrustedSource` 按 source_version 前缀识别，
查询时整批排除。过滤发生在 Pages Functions 的查询层
（`functions/api/platform/v1/commerce-facts/`），所有读取方一次生效，不必每个页面各自
记得排除。数据留在库里可审计，重采成功后自然被可信来源顶上。

### 顺带修掉一个现行 bug

事实行的 `id` 里含 `batch_id`，而 batch_id 取自文件内容哈希——**重采不会覆盖旧行，
只会再插一条**。这既是同一业务日堆积多行的原因，也会一直复现。原先查询按 `f.id`
排序取第一条，取到哪条全看哈希：07-27 面板上显示的很可能正是那条 GMV 61400、
成交订单数为空的半成品。

现在查询带上批次完成时间，`store_daily` 按业务日只保留最新批次那条。其余资源一天多行
是正常的（一个商品 / 一场直播一行），只过滤不可信来源。

### 还没做的：把那 12 行删掉

读取时过滤已经止住错值外泄，但行还在库里。真正删除需要单独授权——那是对生产库的
批量删除，「把历史处理掉」说的是目标，没有指名表与动作。届时先落盘备份，
再按 source_version 前缀删。
