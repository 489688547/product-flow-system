# ADR：公司日常 Chrome 扩展作为网页采集默认入口

## 状态

已接受，2026-07-25。

本决策取代 `2026-07-25-dedicated-browser-collection.md` 的默认运行方式，但保留其中关于固定来源、
本机长任务处理、受控 API 入库、任务租约、检查点和安全诊断的边界。

## 背景

公司日常 Chrome 已经登录快麦、抖店和电商罗盘。真实采集时，默认启动独立 Profile 会丢失已有
登录态，要求员工重复登录；同时形成“日常 Chrome、专用 Chrome、本机服务”三个运行入口，
增加了任务领取、人工恢复和状态解释的复杂度。

MV3 扩展已经能够在公司日常 Chrome 中打开固定页面、核对店铺、读取白名单指标和触发官方下载。
耗时和容易中断的工作已经由本机服务承担，不需要依赖 Service Worker 长时间存活。

## 决策

- 公司 Mac 的常驻采集器默认使用 `extension` 模式，复用公司日常 Chrome 的既有登录态。
- Chrome 扩展只承担短页面动作：固定页面打开、登录/验证判断、店铺 ID 核对、日期选择、
  白名单指标读取和官方报表下载。
- 本机服务继续承担等待下载、文件稳定、原始归档、解析、业务日校验、分块上传、幂等、
  检查点、重试和通知。
- 专用持久 Profile 保留为显式 `dedicated` 回退模式，仅用于多账号必须隔离、日常 Profile
  无法稳定使用或平台风控要求独立环境的场景。
- 两种模式继续共享同一任务租约；任何时刻只能有一个执行器领取同一任务。
- 页面和数据同步默认文案描述“公司 Chrome 扩展”；仅当 runner 实际上报
  `dedicated_browser_*` 时显示专用 Chrome 状态。

## 安全与数据边界

- 扩展不读取或上传 Cookie、Token、密码、验证码、完整页面、网络响应或客户个人信息。
- 任务不能下发任意 URL、脚本、选择器、数据库标识或 D1 binding。
- 店铺任务领取仍携带扩展最近核对的稳定 `storeId`，不匹配时停止采集，避免串店。
- Chrome 和本机服务都不直连 D1；标准事实只能通过受控 Pages Functions ingest 写入。
- 只有完整批次成功才替代上一可信批次并推进游标；失败必须保留任务和安全错误摘要。

## 运行与回滚

- LaunchAgent 安装和 CLI 未显式指定模式时都使用 `extension`。
- 本机服务离线与 Chrome 扩展离线分别上报，`queued` 只表示等待领取。
- 扩展故障时可以显式以 `--browser-mode dedicated` 重装常驻采集器；恢复后再切回默认模式。
- 已完成批次、原始归档、运行记录和游标在模式切换时全部保留。

## 结果

日常采集直接利用员工已经维护的登录态，减少重复登录和错误窗口。MV3 只做短动作，本机继续承担
所有耗时工作，因此不把长任务可靠性重新压回扩展。专用 Profile 仍可用于明确的账号隔离，
但不再强迫单店铺日常采集走第二套登录环境。
